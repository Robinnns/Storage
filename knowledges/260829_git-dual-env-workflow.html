Git 双环境并行开发 — 机制与常用流程

260829 · git双环境工作流mergerebase同步

🔑 核心心智模型

git 是分布式的——你本地看不到远程实时状态。 `origin/main` 只是一个"书签"，记录上次 fetch 时远程的样子。所有同步的本质：改完即 push + 对端 pull，通过共同基线让两端历史会师。

1. 场景：两套环境并行

macOS（写 RTL/约束/笔记）↔ GitHub 仓库 ↔ Windows（跑 Vivado：仿真/综合/下载）。两端都往同一个 main 分支提交。关键前提：Vivado 生成物（.xpr .bit .runs/）已在 .gitignore 忽略——git 只同步"设计决策"，不同步"机器状态"。

2. 两个心智模型

① 书签模型：origin / origin/main / origin/HEAD

术语是什么什么时候动能改吗
origin远程仓库的本地别名（指向 URL）remote set-url 时改地址
origin/main远程 main 的"书签"（远程跟踪指针）fetch/pull 时⛔ 只读
main你的本地工作分支commit 时✅

git status 的 "up to date / ahead / behind" 全是拿本地 main 对比 书签算出来的——书签没刷新，status 就是"过时的真相"。

② 三区模型

工作区（磁盘） ──git add──▶ 暂存区 Index ──git commit──▶ 仓库 HEAD 修改在这里 待提交清单（可分批打包） 固化进历史

commit 只固化"暂存区清单"，不是收走全部工作区改动。反悔用 git restore --staged <文件>。

3. 标准同步流程

# ── A 机（如 macOS）工作结束 ──
git add <要共享的文件>      # 精确 add，别 git add .
git commit -m "描述改动"
git push

# ── B 机（如 Windows）开工前（先设一次默认）──
git config pull.rebase false   # 分叉时默认用 merge（保留合并提交）
git pull                       # = fetch（刷新书签）+ merge

4. 分叉的三种命运（核心机制）

当两端各有提交、互不为祖先（status 显示 [ahead N, behind M]），git 无法直接同步，三种协调方式：

方式机制历史形状合并提交改 hash？
fast-forward本地是远程祖先，指针直推直线无否
merge找共同祖先，把两线绑在合并提交上保留 Y有否
rebase把本地提交"换基"重放到远程之上抹平 Y 变直线无是

rebase 为什么改 hash？ 提交 hash = f(内容, 父提交, 时间戳, 作者, message)。父变了 hash 就变——"重写历史"的含义。因此铁律：已推送的提交绝不 rebase（否则对端还留着旧 hash，历史分裂成平行宇宙）。rebase 只用于本地未推送的提交。

5. 本次实战回放（真实 hash）

macOS 与 Windows 各自提交、分叉自共同祖先 faa7ef3：

* 4877331 Merge branch 'main' ← 合并提交（ort 策略自动合并，零冲突） |\ | * b26dda9 新增tcl ← Windows（含 created_from_gui.tcl 514 行） * | 4653917 新增知识点... ← macOS（Xilinx 器件命名规则） |/ * faa7ef3 更改图片命名格式 ← 共同祖先（merge base）
  1. git fetch：书签 faa7ef3 → b26dda9，status 从 "up to date" 变 "behind 1"
  2. git commit：本地 main → 4653917，历史分叉（ahead 1, behind 1）
  3. git pull --no-rebase：merge 找共同祖先，文件不重叠 → 自动生成合并提交 4877331
  4. git push：远程 b26dda9 → 4877331 快进，两端一致

零冲突的关键：两端改的文件不重叠（macOS 改 knowledges/，Windows 加 created_from_gui.tcl）。

6. 冲突处理

git pull   # 报冲突
git status # 找冲突文件
# 打开文件，删掉标记行手动合并:
#   <<<<<<< HEAD      ← 你的版本
#   =======               ← 分隔
#   >>>>>>> 远程       ← 对方版本
git add <文件>
git commit -m "resolve conflict"
git push
# 或以某一方为准: git checkout --ours / --theirs <文件>

7. 常用命令速查

命令作用时机
git status看工作区/暂存区/领先落后一切操作前
git fetch只刷新书签，不动工作区想先看远程有啥
git pull= fetch + merge（或 rebase）开工前同步
git push本地提交送远程，远程快进工作结束
git add <文件> / git commit工作区→暂存区→仓库提交
git log --graph --oneline可视化历史分叉/合并理解两端关系
git log HEAD..origin/main远程领先我的提交看落后内容
git log origin/main..HEAD我领先远程的提交看待推送内容
git stash暂存工作区改动（临时调试用）切走前藏起来
git restore --staged <文件>撤销 add（退回工作区）反悔暂存
⚠️ 纪律与陷阱
  1. 改完即 push，别攒——攒得越多分叉越大、冲突概率越高。
  2. 同一份被跟踪文件，同一时刻只允许一台机器改；Windows 的临时调试改动用 stash 或不提交。
  3. 生成物永不入库（.xpr/.bit/.runs 已 gitignore），勿 git add -f。
  4. 已推送的提交绝不 rebase。
  5. 网络：GitHub 连接时通时断（SSL_ERROR_SYSCALL），pull/push 失败重试即可，失败无损。
